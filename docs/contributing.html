Contributing Guide

NextGSim is a 5G UE/gNB simulator in Rust (3GPP Rel-15 baseline + selected Rel-17/18 features; the 6G crates are research prototypes, disabled by default). This guide covers everything from a clean machine to a merged pull request.

What to work on Environment Building Testing Code style 3GPP references Submitting a PR Getting merged License & DCO

1. How to contribute — finding work

  • Good first targets: rows marked partial or prototype in the supported-features matrix (gNB and UE), each with its governing spec.
  • Known gaps: docs/6g-gap-analysis.md and docs/gap-protocols.md list missing procedures and wire-conformance gaps (e.g. NTN prototypes not yet wired into live signaling).
  • Bugs & proposals: open a GitHub issue first for significant changes (new procedures, new crates, protocol-behavior changes).

2. Clone & provision your environment

ToolVersionPurpose
Ruststable (≥1.75)Build toolchain
Docker + docker-compose≥24E2E testing with NextGCore
# macOS (Homebrew) — Linux: use rustup.rs brew install rustup && rustup toolchain install stable # Fork on GitHub, then: git clone https://github.com/<you>/nextgsim.git && cd nextgsim

Pure Rust, zero C dependencies — no protoc, libsctp, or ASN.1 compiler needed.

3. Building

cargo build --workspace # debug cargo build --workspace --release # release: nr-gnb, nr-ue, nr-cli cargo build -p nextgsim-ue # a single crate # Lean 5G-only UE (no 6G overhead) cargo build --release -p nextgsim-ue --no-default-features

4. Testing

cargo test --workspace # all unit + integration tests cargo test -p nextgsim-ue # one crate cargo test -- --nocapture # with log output # E2E against a running NextGCore stack cd ../nextgcore/docker/rust && docker compose up -d && cd - cargo test -p nextgsim-tests --features e2e

Honesty rule: E2E validation runs against the matched NextGCore — it proves internal consistency, not third-party conformance. Where an encoding is sim-internal/bespoke (several Rel-17/18 and all 6G prototypes), say so in the module doc comment.

5. Code style & pre-commit checklist

cargo fmt --all cargo clippy --workspace -- -D warnings cargo test --workspace cargo audit # cargo install cargo-audit
  • Zero clippy warnings and zero cargo fmt diffs — CI enforces both.
  • New procedures need unit tests; AI crates that need models load them from tests/models/ (none ship in the repo).

6. 3GPP specification references

Every protocol module carries a doc comment citing its spec. When adding protocol logic cite the exact TS and section: TS 24.501 (NAS), TS 38.331 (RRC), TS 38.413 (NGAP), TS 38.322 (RLC), TS 23.256 (UAV), TS 23.304 (ProSe). 6G prototypes cite the Stage-1 study they model (e.g. TR 22.837 ISAC, TR 22.870 agents) and must be labeled non-normative.

7. Submitting a pull request

  1. Create a feature branch from main with a descriptive name.
  2. Keep PRs small and focused — one logical change per PR.
  3. Use conventional-commit titles naming the component and spec item:
feat(gnb): add MBS NGAP session start procedure (TS 38.413 §8.21) fix(ue): apply NAS security after SecurityModeComplete test(prose): add relay selection RSRP unit test
  • Sign every commit: git commit -s → Signed-off-by: Your Name <email> (Developer Certificate of Origin).
  • Never include AI attributions (e.g. Co-Authored-By bot trailers).
  • The PR description should state what changed, why, the governing 3GPP TS/TR item, and how it was tested.

8. Getting your PR merged

CI must be green before review: build check, cargo test --workspace, cargo clippy, and cargo fmt --check run on every push. A maintainer reviews for correctness, spec fidelity, and test coverage; address review comments with follow-up commits. Docs changes to docs/ deploy to this site on release or manual dispatch of the Deploy to GitHub Pages workflow.
